CONSULTA 2: Receita total e ticket médio por mês (últimos 12 meses)
================================================================================

SQL EXECUTADO:
SELECT 
    TO_CHAR(data_conclusao, 'YYYY-MM') AS mes,
    COUNT(*) AS qtd_agendamentos,
    ROUND(SUM(total_geral)::numeric, 2) AS receita_total,
    ROUND(AVG(total_geral)::numeric, 2) AS ticket_medio
FROM agendamento
WHERE status = 'Concluido'
  AND data_conclusao IS NOT NULL
  AND data_conclusao >= CURRENT_DATE - INTERVAL '12 months'
GROUP BY TO_CHAR(data_conclusao, 'YYYY-MM')
ORDER BY mes DESC;

PLANO SEM ÍNDICES:
[COLAR SAÍDA DO EXPLAIN ANALYZE AQUI]

DIAGNÓSTICO:
Tipo de varredura: [esperado: Seq Scan]
Nó mais custoso: [Filter na coluna status e data]
Tempo total: [_____]
Linhas processadas: [_____]
Divergência linhas/estimado: [avaliar]

CANDIDATOS A ÍNDICE:
1. (status, data_conclusao) - combinado, pois ambos aparecem no WHERE
2. (status) isolado - se seletividade é alta (~50% das linhas são 'Concluido')
3. (data_conclusao) isolado - para range queries

ANÁLISE ESPERADA:
- Status = 'Concluido' filtra ~55% dos registros (baixa seletividade)
- Range de 12 meses pode incluir muitos agendamentos
- Se ~3500 agendamentos totais × 55% = ~1925 linhas processadas
- Seq Scan de 3500 linhas vs Index Range Scan de 1925 é borderline
- Bitmap Heap Scan combinado seria ideal se múltiplos índices existem

DECISÃO:
Criar índice composto em (status, data_conclusao) DESC
Razão: Ambos os predicados aparecem no WHERE. Índice composto é mais eficiente
que dois índices separados, reduzindo I/O de buffer e permitindo index-only scan.

CREATE INDEX idx_agendamento_status_data_desc 
ON agendamento(status, data_conclusao DESC)
WHERE status = 'Concluido';  -- Índice parcial, apenas registros relevantes

CONSULTA 3: Top 10 tipos de serviço mais realizados
================================================================================

SQL EXECUTADO:
SELECT 
    ts.id_tipo_servico,
    ts.descricao,
    SUM(isv.quantidade) AS qtd_execucoes,
    ROUND(SUM(isv.total)::numeric, 2) AS faturamento
FROM item_servico isv
JOIN tipo_servico ts ON isv.id_tipo_servico = ts.id_tipo_servico
GROUP BY ts.id_tipo_servico, ts.descricao
ORDER BY qtd_execucoes DESC, faturamento DESC

CONSULTA 4: Ranking de funcionários por faturamento
================================================================================

SQL EXECUTADO:
SELECT 
    f.id_funcionario,
    f.nome,
    COUNT(DISTINCT isv.id_agendamento) AS qtd_os,
    ROUND(SUM(isv.total)::numeric, 2) AS faturamento
FROM funcionario f
JOIN item_servico isv ON isv.id_funcionario = f.id_funcionario
JOIN agendamento ag ON ag.id_agendamento = isv.id_agendamento
WHERE ag.status = 'Concluido'
GROUP BY f.id_funcionario, f.nome
ORDER BY faturamento DESC;

Tempo total: [_____]
Linhas processadas: [_____]
Estratégia de join: [Hash Join / Nested Loop para cada]

CANDIDATOS A ÍNDICE:
1. (id_funcionario) em item_servico
2. (id_agendamento) em item_servico (provável PK ou FK)
3. (status) em agendamento (filtro crítico)
4. Índice composto em agendamento(status, id_agendamento)

ANÁLISE ESPERADA:
- 2 joins sequenciais; 50 funcionários, ~7000 items
- Filtro WHERE status='Concluido' reduz agendamentos a ~1925
- Se Nested Loop: cada funcionário varredura sequencial em item_servico
- Se Hash Join em primeiro e Index Scan no segundo: melhor

DECISÃO:
Criar índices para acelerar ambos os joins:
1. idx_item_servico_funcionario em item_servico(id_funcionario)
2. idx_agendamento_status em agendamento(status) onde status='Concluido'

CREATE INDEX idx_item_servico_funcionario 
ON item_servico(id_funcionario);

CREATE INDEX idx_agendamento_status_concluido 
ON agendamento(status) 
WHERE status = 'Concluido';  -- Índice parcial

CONSULTA 5: Top 20 clientes por gasto acumulado
================================================================================

SQL EXECUTADO:
SELECT 
    c.id_cliente,
    c.nome,
    CASE WHEN c.cpf IS NOT NULL THEN 'PF' ELSE 'PJ' END AS tipo_cliente,
    ROUND(SUM(p.valor)::numeric, 2) AS gasto_total
FROM cliente c
JOIN veiculo v ON v.id_cliente = c.id_cliente
JOIN agendamento ag ON ag.id_veiculo = v.id_veiculo
JOIN pagamento p ON p.id_agendamento = ag.id_agendamento
GROUP BY c.id_cliente, c.nome, tipo_cliente
ORDER BY gasto_total DESC
LIMIT 20;

Tipo de varredura: [_____]
Nó mais custoso: [qual join? qual table scan?]
Tempo total: [_____]
Linhas processadas: [_____]
Estratégia de join: [primeira join c-v, depois v-ag, depois ag-p]

CANDIDATOS A ÍNDICE:
1. (id_cliente) em veiculo
2. (id_veiculo) em agendamento
3. (id_agendamento) em pagamento

ANÁLISE ESPERADA:
- 4-table join: cliente → veiculo → agendamento → pagamento
- 200 clientes; 500 veículos; 3500 agendamentos; ~5000 pagamentos
- Cada join tem FK natural, mas sem índices é Seq Scan + Hash Join
- Este é o pior caso: múltiplos Seq Scans concatenados

DECISÃO:
Criar índices nas todas as colunas de junção:

CREATE INDEX idx_veiculo_cliente ON veiculo(id_cliente);
CREATE INDEX idx_agendamento_veiculo ON agendamento(id_veiculo);
CREATE INDEX idx_pagamento_agendamento ON pagamento(id_agendamento);

Estas são FKs e devem acelerar significativamente os Nested Loops.

CONSULTA 8: Nota média por funcionário (>= 5 avaliações)
================================================================================

SQL EXECUTADO:
SELECT 
    f.id_funcionario,
    f.nome,
    COUNT(DISTINCT av.id_avaliacao) AS qtd_avaliacoes,
    ROUND(AVG(av.nota)::numeric, 2) AS nota_media
FROM funcionario f
JOIN item_servico isv ON isv.id_funcionario = f.id_funcionario
JOIN avaliacao av ON av.id_agendamento = isv.id_agendamento
GROUP BY f.id_funcionario, f.nome
HAVING COUNT(DISTINCT av.id_avaliacao) >= 5
ORDER BY nota_media DESC;

CANDIDATOS A ÍNDICE:
1. (id_funcionario) em item_servico
